# ANDI → Ana MCP: Single Service Identity + ANDI-Enforced Client Scoping

> **Scope:** how **ANDI** (a separate AI workshop-facilitation app) authenticates to Ana's `/mcp` endpoint with **one** service identity, and how a single ANDI workshop is confined to the one Altus client its configuration links it to — a confinement ANDI enforces in its own MCP tool wrappers, with Ana applying a coarse allowlist ceiling on top.
> **Companion docs:** [mcp-claude-oauth-entra.md](mcp-claude-oauth-entra.md) (the per-user delegated flow Claude uses) and [entra-app-registrations.md](entra-app-registrations.md) (the registrations that front `/mcp` — this design adds exactly one).
> **Status:** direction agreed verbally on the **7 Jul 2026 Altus AI Explorations** call (Stas, Puru, Alex, Igor); refined into an agentic-first integration on the **23 Jul 2026** ANDI↔Ana working session. **Nothing built yet.** A per-workshop-SP alternative (one service principal per workshop, with a `WorkshopPrincipal` binding table in Ana) is retained as the primary escalation path in §9 — where this design goes if Ana-enforced isolation or per-workshop revocation ever becomes a hard requirement. The remaining gate is ANDI's flow definition (§10).
>
> **Permission model:** [entra-scopes-and-roles.md](entra-scopes-and-roles.md) is the authoritative list; this doc has been reconciled to it. In short: ANDI's config picker lists clients by calling the **REST clients endpoint via OBO with `user-access`** — the same endpoint and scope the Ana frontend uses — and its data plane calls `search_documents` / `fetch_document` over `/mcp` via its SP with the **`Mcp.Documents.Read`** app role. There is no `Clients.Read` app role and no app-only listing (services never enumerate); the picker is a delegated/OBO REST call, user-scoped.

## 1. The core idea

Ana is a **resource server, not an identity provider**. Authentication belongs to Entra ID — that was the call's firmest conclusion (Stas, 10:35:34: *"All token generated by the client. Anna just verifies the token."*). Standing up a second, Ana-proprietary credential system alongside Entra would fork the platform's identity infrastructure at exactly the moment it is cheapest not to (Stas, 10:48:37).

ANDI holds **one** Entra identity — a single app registration and service principal — and calls `/mcp` on its own behalf via the client-credentials grant. It is not one identity per workshop. Everything ANDI does against Ana's data plane travels on that one token.

That single token proves *ANDI is calling*. It does **not**, on its own, prove *for which client*. The client is decided elsewhere and enforced in two places, weakest-outermost:

- **ANDI decides and pins the client.** Each workshop in ANDI's own configuration stores an `anaClientId`. ANDI is the MCP *client*: its backend runs the agentic loop, and it exposes **tool wrappers** to the model that omit `clientId` entirely. The model can never choose a client — the wrapper injects the workshop's pinned `anaClientId` into every `search_documents` / `fetch_document` call as it leaves ANDI. This is the real workshop→client boundary, and it lives in ANDI's code (§6).
- **Ana applies an allowlist ceiling.** Ana resolves ANDI's app identity to the set of clients ANDI is permitted to reach at all, and rejects any `clientId` outside it. This is a coarse guard — "may ANDI touch this client" — not "is *this workshop* entitled to this client." Ana cannot see workshops; it sees one app and a `clientId` argument.

### The invariant this design consciously relaxes

The 7 Jul call adopted a hard invariant (Alex, 10:44:26): *one token per request, and the permitted client is determined by the token.* **This design does not satisfy that invariant, and does so deliberately.** Here the client is *asserted by ANDI* (within its allowlist), not *determined by the token*. A `clientId` argument is trusted from ANDI as long as it falls inside ANDI's allowlist — it is exactly the "ANDI enforces the restriction internally" option Alex flagged as *"simpler, but it's riskier"* (10:26:39).

Three things make that trade acceptable for the MVP, and they are the whole justification for choosing this over the per-workshop design (§9):

1. **The compromise blast radius is identical either way.** ANDI-as-a-system spans every client it runs workshops for (Alex, 10:38:17). In *any* design, ANDI's backend can obtain a data-plane token for every client it serves — per-workshop SPs included, since ANDI owns them all. So per-workshop identity never reduced the "compromise ANDI → all clients" exposure; it only isolated ANDI *bugs* from each other. The token→client invariant buys bug-isolation and revocation granularity, not protection from a compromised ANDI.
2. **Operational cost collapses.** One registration instead of ~120/year. No `Application.ReadWrite.OwnedBy` on Graph, no per-workshop provisioning, no owner-quota ceiling, no propagation-latency race, no `WorkshopPrincipal` binding table in Ana.
3. **The escalation path is clean and additive** (§9). If Ana-enforced per-client isolation later becomes a requirement, per-client service principals restore it without per-workshop churn; the full per-workshop design restores instant revocation and per-workshop audit. Both build *on top of* what this design ships, changing only how `clientId` is authorized, not the wrapper mechanism.

The honest one-line summary: **Ana guarantees "ANDI, and only within its allowlist." ANDI guarantees "this workshop, this client." The workshop→client boundary is ANDI's to keep.**

## 2. The two capabilities (one identity)

There is **one SP** for the data plane, and a **capability split** by Entra *flow*: the catalog is a delegated (OBO) call, the data plane a service call.

| | **Catalog capability** | **Retrieval capability** |
|---|---|---|
| Used for | listing clients so a workshop can be linked to one, at configuration time | every data-plane call a workshop makes |
| Surface | the **REST clients endpoint** (`/api/clients`, the one the FE uses) | `search_documents` / `fetch_document` over `/mcp` |
| Grants | the **signed-in user's** clients: id + name, no document access | documents for **one client per call**, the `clientId` ANDI injects |
| Flow | **OBO** — a token for the signed-in Ana user | **client-credentials** — the ANDI SP |
| Authorized by | `user-access` scope (delegated / OBO) — exactly the FE's path | `Mcp.Documents.Read` app role **+** `clientId ∈ ANDI allowlist` |
| Identity | the signed-in Ana user (acquired by ANDI via OBO) | the single ANDI service principal |

The catalog is a **REST** call (OBO, `user-access`, the FE's existing path); the data plane is a **`/mcp`** service call. They differ by both surface and flow — OBO for the human-driven picker, client-credentials for the headless data plane.

### The two Entra flows, and not mixing them

Stas drew a distinction (10:40:56 — *"We are mixing two different modes, and that's important"*) that still governs:

- **On-behalf-of** — a human drives ANDI, ANDI acquires a token *for that user*, and the user's own access governs what is reachable.
- **Service / client credentials** — ANDI acts on its own behalf, no user in the loop.

The data plane is **service** flow, always — the single ANDI SP via client credentials. Workshop participants are email invitees to ANDI, not Entra users (Puru, 10:45:01), and their feedback is processed by ANDI as a service, not on any participant's behalf (Alex, 10:46:06).

**Configuration-time client selection is where OBO belongs, and this design uses it** (§5.5). Whether a given Ana user may point a workshop at client X is an authorization decision about *their* access — so the picker calls the **REST clients endpoint via OBO for the signed-in Ana user** (with `user-access`, the FE's path), and the result is that user's own clients. This closes the "any ANDI user binds any client ANDI can reach" gap structurally: an ANDI user can only bind clients they can already see in Ana, not ANDI's whole allowlist.

## 3. The actors

| Actor | Identity | Role |
|---|---|---|
| **Entra ID** | tenant `e99365e9-…` | Issues ANDI's single app-only token. |
| **ANDI backend** | **one** Entra app registration + SP (client ID TBD) | The MCP *client*. Holds the workshop→`anaClientId` mapping. Exposes clientId-stripped tool wrappers to the model and injects the pinned client on execution. Calls `/mcp` and the clients REST endpoint. |
| **Ana user linking a workshop** | existing Ana user (in ANDI's UI) | Picks which client a workshop points at, from the client picker. |
| **MCP server** | `/mcp` on the Ana API | OAuth 2.0 protected resource. Same endpoint Claude uses; gains an app-only path with an allowlist check. |
| **Clients REST endpoint** | ordinary Ana API, outside `/mcp/*` | Feeds the config-time picker via ANDI's **OBO `user-access`** token — the same endpoint and scope the FE uses; no change needed (§5.5). |

Note what this design **does not require**: no per-workshop app registrations, no workshop service principals, no `WorkshopPrincipal` binding table, no Graph write access held by ANDI.

## 4. The end-to-end flow

### 4.1 Workshop configuration (rare, human in the loop)

```
Ana user            ANDI backend                         Ana
   │                     │                                 │
   │ create workshop     │                                 │
   │  (signed in to ANDI) │  OBO: token for THIS user, user-access
   ├────────────────────▶│ GET /api/clients (Bearer OBO)   │
   │                     ├────────────────────────────────▶│ REST /api/clients
   │                     │   Ana: delegated scp → the user's own clients
   │                     ◀────────────────────────────────┤   (same as the FE)
   │  pick client X      │                                 │
   │                     │ store Workshop.anaClientId = X   │
   │                     │  (in ANDI's own database)        │
```

The workshop→client mapping is written **in ANDI**, never in Ana. Ana learns of `X` only when a data-plane call arrives carrying it.

### 4.2 Data plane (frequent, no human)

```
ANDI, running workshop W (anaClientId = X)            Entra / Ana
   │  client_credentials as the ANDI SP                   │
   │  scope=api://<AiAssistantApi>/.default                │
   ├─────────────────────────────────────────────────────▶ Entra
   ◀───── token: aud=AiAssistantApi, roles=[Mcp.Documents.Read] ─────
   │                                                       │
   │  agent loop: model emits search_documents(query)      │  ← no clientId; the model
   │  wrapper injects clientId = X (the workshop's pin)     │    never sees or sets it
   │  Authorization: Bearer <ANDI token>                    │
   ├─────────────────────────────────────────────────────▶ Ana /mcp
   │  Ana: validate JWT (issuer, audience, signature)      │
   │  Ana: roles contains Mcp.Documents.Read → admitted     │
   │  Ana: ClientScopeResolver → allowlist(ANDI)            │
   │        X ∈ allowlist ? run against X : 403             │
   ◀─────────────────────────────────────────────────────┤
```

**The `clientId` Ana runs against is the one ANDI put in the request.** Ana's only veto is the allowlist: it can refuse a client ANDI may not touch at all, but among permitted clients it trusts ANDI's choice. That the request carries `X` and not some other workshop's client is guaranteed by ANDI's wrapper, not by the token (§1, §6).

## 5. What Ana must build

### 5.1 One registration, one app role + a delegated permission

**ANDI's app registration** on `AiAssistantApi` (`4279cecc-…`) needs two grants, assigned once by an admin:

- `Mcp.Documents.Read` — an **app role** (`allowedMemberTypes: ["Application"]`), for the SP's client-credentials data-plane calls (`search_documents` / `fetch_document`).
- `user-access` — the **delegated scope**, for the OBO config picker: ANDI exchanges the signed-in user's token and calls the **REST clients endpoint** on their behalf, exactly as the FE does. Admin-consented so ANDI users see no prompt.

There is **no `Clients.Read` app role** — services never enumerate clients (§5.5, §5.6); the picker's listing is delegated/OBO on the existing REST endpoint, and the data plane's client is the one ANDI pins.

The app role, rather than a scope, is not cosmetic: app-only tokens carry `roles`, delegated tokens carry `scp`. The existing policy inspects `scp` and will reject the SP's app-only token no matter how it is configured (§8, first row) — hence the policy change in §5.2.

There is **no role-less identity** and **no reliance on Entra issuing tokens to unauthorized principals**. ANDI is explicitly assigned its role and scope; "assignment required" on `AiAssistantApi` is compatible with this design and can be left on.

### 5.2 `McpInvoke` policy

[Program.cs](../altus-ai-assistant/AltusAiAssistantApi/Program.cs) — today the policy only inspects `scp` for `Mcp.Invoke`. Extend it to admit one further principal shape:

| Principal | Admitted on | Reaches |
|---|---|---|
| delegated user (Claude) | `scp` contains `Mcp.Invoke` | all `/mcp` tools, incl. `list_clients` (user-scoped) |
| ANDI app identity (SP) | app-only + `roles` contains `Mcp.Documents.Read` | document tools only, any client in ANDI's allowlist |

(ANDI's OBO picker does not hit `/mcp` — it calls the REST clients endpoint with `user-access`, §5.5 — so it is not admitted by this policy.)

The delegated path is unchanged. No policy-scheme selector and no second authentication handler: every token here is a JwtBearer token from Entra.

### 5.3 The ANDI client allowlist

The set of clients ANDI may reach. There is no per-workshop row — only per-app scope.

Two shapes, in order of increasing effort:

- **Config-only (MVP).** ANDI's `appid`/`oid` → an allowlist in Ana configuration. Simplest; a change is a config deploy. Fine if the allowlist is stable (e.g. "all clients," or a small fixed set).
- **Table-backed.** An `AppClientGrant` table keyed on ANDI's `oid`, one row per permitted client, editable by an Ana admin at runtime. Warranted once the allowlist changes often enough that redeploying config is friction.

Key any table on the token's **`oid`** (identical to `sub` for an app-only token): stable, unique, Entra-asserted, and in the restricted claim set, so no policy can remap it. `appid` also works but identifies the application object rather than the local SP; prefer `oid` for consistency with the delegated path.

**If the allowlist is "all clients," Ana's ceiling is effectively a no-op** and the boundary is entirely ANDI's (§6). That is an accepted MVP posture, not a bug — but it is the reason the per-client escalation (§9) exists.

### 5.4 `ClientScopeResolver`

[ClientScopeResolver.cs](../altus-ai-assistant/AltusAiAssistantApi/Mcp/ClientScopeResolver.cs) — today it reads the user's `oid`, looks up `UserClient` rows, and validates the requested `clientId` against that set. Add an app-only branch:

- **ANDI app identity** → resolve `oid` → the allowlist (§5.3). The `clientId` argument is **required** on document tools (there is no per-token binding to default from); require `clientId ∈ allowlist`, else `ForbiddenAccessException`.

The delegated path is untouched. The resolver does **not** pin `clientId` to a single value — it *validates membership*. The single-value pin lives in ANDI's wrapper, not here.

### 5.5 Client listing for the config UI

The picker calls the **existing REST clients endpoint** that Ana's own FE already consumes — via **OBO with `user-access`** for the signed-in Ana user. ANDI exchanges that user's token for one carrying `user-access` and calls `/api/clients` exactly as the FE does. The result is **that user's own clients** (delegated result-scoping), so an ANDI user can only bind clients they can already see in Ana — never ANDI's whole allowlist. This is chosen for:

- **Reuse of a proven contract.** The clients endpoint already backs the FE's human-facing dropdown, so it is a stable, stress-tested REST contract — nothing new to build or version. A plain UI list with no model in the loop gains nothing from MCP's tool surface.
- **Structural user-scoping.** Because the token is delegated (OBO), Ana returns the user's `UserClient` rows and cannot widen — the binding-authority gap (§6) is closed in the auth layer, not left to ANDI.
- **Same identity plumbing everywhere.** ANDI already acquires a user token to sign the person in; the OBO exchange to `user-access` reuses it.

**No Ana-side change is needed** — the REST clients endpoint already accepts `user-access` (the FE uses it), and ANDI's OBO token carries `user-access`. There is **no `Clients.Read` app role and no app-only listing**: a *service* token (the SP) never lists clients (§5.6), because a service always knows its client and an app-only list would leak the app's whole allowlist. ANDI thus uses `/mcp` (SP) for the data plane and REST (`user-access`, OBO) for the config picker.

### 5.6 Tool-level shape

`search_documents` / `fetch_document` must accept and honor an explicit `clientId` from an app identity, validated per §5.4. `list_clients` over MCP is **not used by ANDI** (its picker uses the REST endpoint, §5.5); it stays a delegated-only tool for Claude, gated to a delegated `scp` and filtered out of `tools/list` for any app token, so the SP can never call it. That is the one tool-level split by identity: services get `search`/`fetch`; human/Claude tokens additionally get `list_clients`.

### 5.7 Telemetry

`McpTelemetry` logs `userObjectId` / `userPrincipalName` for the delegated path. For ANDI, log the ANDI `oid` + the **resolved `clientId`** + any **ANDI-supplied workshop label** (a request header or argument ANDI attaches for audit — untrusted, but useful for correlating with ANDI's own logs). Confirm this satisfies audit; note that Ana alone cannot attribute a call to a workshop — that attribution lives in ANDI (§6).

## 6. What ANDI must build — the tool wrappers (specified here because the boundary lives here)

Because Ana no longer pins the client, **the workshop→client boundary is entirely ANDI's tool-wrapper layer.** It is specified here so Ana's reviewers can see exactly what they are trusting.

- **Single token provider.** `client_credentials` as the one ANDI SP, `scope=api://<AiAssistantApi>/.default`, token cached ~1h and refreshed ahead of expiry. One implementation, no per-workshop keys.
- **Model-facing tools omit `clientId`.** The tool schemas handed to the model have no `clientId` parameter — the model emits only `query` / `documentId`. Choosing a client is a data-boundary decision, never a reasoning one.
- **The executor injects the pin.** A guarded executor (`execGuarded`) reads `Workshop.anaClientId` from ANDI's own config and sets `clientId` on every outgoing MCP call. It also clamps sizes (`fetch_document` `maxChars`, result truncation) and bounds the agent loop (`maxSteps`, wall-clock).
- **Fail soft, log the trajectory.** The runner sits behind fire-and-forget callers, so an Ana outage degrades to "no background knowledge," never a failed workshop action. Persist the per-run tool-call sequence (tool, args incl. injected `clientId`, result size) — the only way to debug a bad enrichment, and the only per-workshop audit trail that exists, since Ana's is per-app.

The concrete shape (a clientId-stripped tool table, an `execGuarded` that injects `anaClientId`, and a bounded loop) is the agentic-first design from the 23 Jul session; swapping the underlying transport from MCP to a REST retrieval endpoint would change nothing above the executor, which is why "MCP vs REST" is an ANDI-side integration choice, not an auth-model one.

**Where the isolation boundary sits — and its honest limits:**

- **The client boundary is ANDI's code, not Ana's.** Ana's allowlist is a ceiling ("may ANDI touch client X"), not the per-workshop boundary. A bug in `execGuarded` that injects the wrong workshop's `clientId` is **not caught by Ana** if the wrong client is also in ANDI's allowlist. In the per-workshop design that same bug was structurally impossible; here it is a code-correctness obligation on ANDI.
- **Compromising ANDI compromises every client in its allowlist** — the same exposure as the per-workshop design (§1), since ANDI held all those credentials there too.
- **Binding authority follows the picker's scoping — and the picker is OBO-scoped (§5.5).** Because the picker lists via OBO against the REST clients endpoint (`user-access`), an ANDI user can only bind clients they can already see in Ana, not ANDI's whole allowlist.
- **Ana cannot attribute a call to a workshop.** It sees one app and a `clientId`. Per-workshop audit and per-workshop revocation do not exist on Ana's side (§8); both live in ANDI or require the §9 escalation.

## 7. Token and identity lifecycle

- **One identity.** Short-lived app-only tokens, acquired and refreshed automatically by ANDI. Nothing long-lived is stored in Ana — no secret, no token, no hash. Ana holds only the allowlist.
- **Revocation is all-or-nothing at Ana's edge.** Disabling the ANDI SP, or removing its `Mcp.Documents.Read` role, cuts off **every** workshop at once. Narrowing access to *one* client is done by editing the allowlist (removing that client), which affects every workshop pointed at it. **There is no per-workshop revocation** — the price of one identity. If a single workshop must be stopped without touching others, that is done in ANDI (disable the workshop), or via the §9 escalation.
- **No provisioning, no cleanup, no quota.** No per-workshop directory objects means none of the owner-quota (§9), soft-delete, or propagation-latency concerns apply.
- **Open:** the workshop→client mapping lives in ANDI, so Ana has no lifecycle hook when a workshop closes or a user loses access to the bound client. If those cascades matter, they are ANDI's to build, or a reason to escalate (§9).

## 8. Failure modes & how to read them

| Symptom | Likely cause | Where to look |
|---|---|---|
| `401` on `/mcp` with the ANDI token | wrong audience, or `requestedAccessTokenVersion` still `null` → v1 token with an `sts.windows.net` issuer | §5.1; same trap documented for voice in [entra-app-registrations.md](entra-app-registrations.md) §6 |
| `403` with a valid ANDI token on `/mcp` | policy still inspecting `scp` only — app-only tokens carry `roles` | §5.2 |
| `403` on the REST clients endpoint with ANDI's OBO token | the OBO exchange didn't yield `user-access` (consent/permission missing) | §5.1, §5.5 |
| `403` on `search_documents` / `fetch_document` | `clientId` argument is outside ANDI's allowlist (or omitted — it is required for the app identity) | §5.3, §5.4 |
| A workshop reads the **wrong** client (but within the allowlist) | `execGuarded` injected the wrong `anaClientId` — **Ana will not catch this** | §6; this is the boundary that is ANDI's to keep |
| Need to stop one workshop, but only all-or-nothing revocation is available | expected — no per-workshop revocation with one identity | §7; disable the workshop in ANDI, or escalate (§9) |

## 9. Why not the alternatives

- **Per-workshop service principal + `WorkshopPrincipal` binding in Ana.** Entra issues one SP per workshop; Ana pins each token's `oid` to exactly one client via a binding row. **Strictly stronger isolation** — Ana, not ANDI, guarantees workshop→client, an `execGuarded` bug cannot cross clients, revocation is an instant per-workshop DB flag, and audit is per-workshop at Ana. Deferred, not rejected, on cost: ~120 registrations/year, `Application.ReadWrite.OwnedBy` on Graph, owner-quota ceilings, per-workshop provisioning with propagation-latency handling, and a binding table with its own authorization surface. **This is the primary escalation path** — adopt it when Ana-enforced per-workshop isolation, or instant per-workshop revocation, becomes a hard requirement.
- **Per-client service principal** (one SP per Altus client, not per workshop). The middle ground. Restores **Ana-enforced** token→client isolation — each token is pinned to one client, so an ANDI bug cannot cross clients — without per-workshop churn (one SP per client, a low and stable count). Loses per-*workshop* revocation and audit (add a workshop label in Ana for the latter). The right next stop if the allowlist-ceiling weakness (§6) bites before full per-workshop granularity is needed.
- **Entra emits the client as a custom claim.** Mechanically possible over the SP's `tags`, mechanically useless: the claim is a property of the *principal*, not the *request*, so it still implies one SP per binding — at which point `oid` conveys it for free. See the appendix. Irrelevant to a single-SP design anyway, since one SP cannot carry a per-workshop claim.
- **Ana mints every credential; Entra is not involved.** Makes Ana a second identity provider — the thing the call steered away from (Stas, 10:48:37). The single-SP design keeps Entra as the sole issuer with far less machinery.
- **A plain REST endpoint instead of MCP for retrieval.** Viable for pure retrieval, but ANDI's workshop facilitation is an **LLM agent** driving an `search`/`fetch` loop, and MCP is the tool surface Ana already exposes with client scoping — reusing `/mcp` keeps one data-plane surface. The catalog picker, by contrast, *does* use REST (`/api/clients` via OBO `user-access`, §5.5) — a plain UI list with no model, so it reuses the FE's existing endpoint rather than MCP `list_clients`.
- **The client travels beside the token** — a side header or `workshopId` Ana looks up. This design is *close* to this (ANDI asserts `clientId`), and accepts it knowingly for the MVP — but bounds it with the allowlist so ANDI cannot assert an arbitrary client, only one it is already permitted. The unbounded version (Ana looks up a workshop it knows nothing about) is still rejected.
- **On-behalf-of per participant.** Participants aren't Ana users, have no `UserClient` rows, aren't in Entra (Puru, 10:45:01). The scoping needed is workshop→client, not participant→client.

## 10. ANDI's usage flows

Stas made this the gating item (10:49:33): *"the main question right now [is] to understand Andy's user flows... starting from this, we can then configure Entra ID."* Igor confirmed (10:49:25) they are not fully pinned down. What follows is what was described, refined on the 23 Jul session — **provisional, to be confirmed with Igor and Adam.**

1. **Client-catalog lookup at workshop-configuration time.** ANDI lists Ana's clients so a workshop can be linked to one. Catalog capability: the REST clients endpoint via OBO (`user-access`), user-scoped — the FE's path; no document access.
2. **Workshop-preparation context seeding.** The workshop prompt (Puru, 10:54:29: *"work out the AI roadmap to reduce call center costs"*) drives an agentic loop of `search_documents` / `fetch_document`. Igor (10:55:54): the agent works out what Ana can offer, chooses what this workshop needs, then requests it — multiple calls, the agent deciding when to stop. Results stored in ANDI and used to enrich later LLM output. `clientId` is the workshop's pin throughout; the model never sees it.
3. **Scheduled context refresh.** A workshop's stored context is re-fetched periodically as Ana's corpus grows (Igor, 10:50:35).
4. **Live enrichment during a workshop** — as participants submit input, ANDI asks Ana for more (Igor, 10:57:19). **Later phase**, the one Puru wants gated (§11).

Participants are email invitees to ANDI rather than Entra users, which is why all of the above is service flow on the single ANDI identity rather than per-participant OBO.

## 11. Cost, throttling & phasing

Puru raised this as a first-class constraint (11:00:56): *"I could very easily see that becoming a $20,000 cost unexpectedly."* An autonomous agent calls far harder than a human, and the calls that cost money are the ones no one is watching.

**Phasing** (Puru, 10:57:33 and 11:02:11):

- **Phase 1 — workshop preparation only, human-triggered.** A bounded number of queries at prep time, launched by a moderator. Latency doesn't matter, so queries can be comprehensive.
- **Phase 2 — live and fully automatic queries.** Gated on throttling and per-workshop quotas existing first.

**Where the limits go.** This is a place the single-SP design pays a small tax. Ana sees one caller, so an Ana-side per-*workshop* quota is not possible from the token alone — Ana can only throttle **ANDI in aggregate** (keyed on the ANDI `oid`), or trust an ANDI-supplied workshop label (§5.7) as an untrusted quota key. **Per-workshop budget enforcement therefore belongs in ANDI** (it already fronts model spend through the Lighthouse proxy; Stas, 11:01:44), with Ana holding a coarse aggregate cap as a backstop. If per-workshop enforcement must live in Ana, that is another pull toward the per-workshop escalation (§9), where the SP `oid` is already per-workshop.

1. **Allowlist shape and breadth.** Config-only or table-backed (§5.3)? And is the allowlist "all clients" (ceiling is a no-op, boundary fully in ANDI) or a curated subset? This choice sets how much §6's honest limit actually bites.
2. **Picker scoping.** Default allowlist picker (any ANDI user binds any reachable client) vs OBO-scoped picker (user binds only what they can see, §5.5). Accept the gap for MVP, or build OBO now?
3. **Per-environment or shared registration?** The voice API is deliberately split per environment ([entra-app-registrations.md](entra-app-registrations.md) §6); Alex flagged shared QA/prod registrations as a general problem (10:03:24). ANDI's single registration should be per-environment, and QA clients must not be in a prod ANDI allowlist.
4. **Revocation granularity.** Is all-or-nothing (plus allowlist editing) acceptable, or is per-workshop revocation a requirement — in which case escalate to §9?
5. **Per-workshop quota** (§11) — enforced in ANDI, or a reason to escalate so Ana can key on a per-workshop `oid`?
6. **Client-admin visibility.** Should a client owner be able to see that ANDI's allowlist includes their client, and veto it?
7. **Catalog payload** — the REST clients endpoint (via OBO `user-access`) returns the user's own clients as id + name. Confirm that shape suffices for ANDI's picker (it already backs the FE dropdown, §5.5).

### Appendix: why the client cannot ride *inside* the single ANDI token

Recorded because the question will be asked — "if ANDI has one token, why not put the client in it per call?" The short answer: **Entra has no request-time downscoping in the app-only path at all**, so a single SP's token always carries the same fixed claims regardless of which workshop is calling.

- Client credentials requires `scope=.default`; there is no way to request a subset of what the principal holds. You cannot mint a "just client X" token from ANDI's SP.
- There is no RFC 8693 token exchange for app-only (OBO is user-context only), and custom claims providers fire on user sign-in, not client credentials.
- Claims mapping over the SP's `tags` emits a property of the *principal*, not the *request* — the same value on every call — and directory extension attributes on application objects are explicitly not emitted in client-credentials tokens.
- `roles`, `scp`, `appid`, `oid`, `azp` are all in the restricted set and unmodifiable by claims mapping.

So with one SP, the token cannot say *which client this call is for* — only *who is calling*. That is precisely why the client is carried as a **request argument** and pinned by **ANDI's wrapper**, with Ana bounding it by the allowlist. To make the *token* carry the client, you need one principal per client (per-client SP) or per workshop (per-workshop SP) — the §9 escalations. This is the mechanical reason those escalations exist, and the reason this design accepts an ANDI-asserted `clientId` for the MVP.
